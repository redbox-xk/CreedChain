Known critical defects (must be fixed in this build):
  C1. No P2P networking — the "chain" is a single node. No gossip,

  C2. Private keys and mnemonics stored in plaintext in the wallets

  C3. Mining is simulated — no real PoW difficulty adjustment, no

  C7. Zero tests. No CI pipeline. No lint/typecheck gate.
  C8. No observability — console.log only. No metrics, no tracing,
      no structured logs.
  C9. No scalability plan — full chain is loaded into memory on
      startup. Memory grows unbounded. No pruning, no SPV.
  C10. Documentation is minimal; no threat model, no runbooks, no
       API reference.

NON-NEGOTIABLE ENGINEERING RULES
═══════════════════════════════════════════════════════════════════════
1.  Every transaction entering the mempool MUST pass full validation:
      - Inputs reference UTXOs that exist and are unspent
      - Each input's scriptSig is a valid ECDSA signature by the
        owner of the referenced UTXO
      - sum(inputs) >= sum(outputs) + fee
      - No duplicate inputs (within tx and across mempool)
    Invalid transactions are rejected with a specific error code.
2.  Every block appended to the chain MUST be validated:
      - Merkle root matches all transaction hashes
      - Header hash < current difficulty target
      - Coinbase reward <= block subsidy + sum(fees)
      - All transactions pass rule #1
      - Parent hash matches the current chain tip (or triggers a
        valid reorg path per rule #6)
3.  All private keys and mnemonics MUST be encrypted at rest using
    AES-256-GCM with a key sourced from env/KMS. No plaintext keys
    in the DB, ever. No plaintext keys in logs, ever.
4.  Every write endpoint (mine, send, create-wallet, admin actions)
    MUST require authentication (JWT). Public read endpoints may
    remain unauthenticated, but MUST be rate-limited.
5.  Every external call (peer gossip, DB) MUST have a timeout and a
    bounded retry policy with structured error logging.
6.  Reorg handling MUST follow longest-cumulative-difficulty rule.
    Reorgs deeper than N blocks (config, default 12) MUST be flagged
    as critical alerts and refuse the reorg until operator override.
7.  No hardcoded secrets. Use process.env everywhere. A `validateEnv`
    module MUST fail-fast at boot if required keys are missing.
8.  Every new module ships with: unit test + integration test +
    docs entry + CHANGELOG.md line.
9.  No console.log in production paths — use the structured logger.
10. Any file > 400 LOC must be split by concern.
11. All crypto operations MUST use well-audited libraries (no
    hand-rolled curves, no custom KDFs). Use secp256k1 (via
    @noble/secp256k1 or elliptic), @noble/hashes for SHA-256,
    @scure/bip32, @scure/bip39.
12. Consensus-critical code paths MUST have >= 90% line coverage and
    a property-based test suite.

──────────────────────────────────────────────────────────────────────
PHASE 1 — CRYPTOGRAPHIC HARDENING & VALIDATION (unblocks everything)
──────────────────────────────────────────────────────────────────────
1.1 Key Vault
    - server/blockchain/keyvault.ts
        * encrypt(plaintext) / decrypt(ciphertext) using AES-256-GCM.
        * Master key from process.env.MASTER_KEY (64 hex chars).
        * Every wallet row stores { iv, ciphertext, tag }, never raw.
    - Migration: encrypt all existing wallets; add columns iv, ciphertext,
      tag; drop mnemonic and private_key columns.
    - Add a rotation script scripts/rotate-master-key.ts that re-encrypts
      all wallet rows under a new master key.
    - NO wallet content is ever serialized into logs or API responses
      (except a one-time reveal endpoint for the authenticated owner,
      rate-limited to 1/min).

1.2 Transaction Validation Engine
    - server/blockchain/validation/transaction.ts
        * verifyTransaction(tx, utxoView, mempoolView): ValidationResult
        * Checks: UTXO existence, unspent, signature match,
          double-spend within tx, double-spend against mempool,
          value conservation, fee >= min_fee_per_kb * size_kb.
    - UTXO view service (server/blockchain/utxo.ts):
        * getUtxo(outpoint): UTXO | null
        * spend(outpoint): void  // called only after block acceptance
        * Efficient lookup by (txid, vout); indexed in DB.
    - Integrate into POST /api/transaction/send: reject with 400 +
      specific error code on any failure. Do NOT add to mempool on fail.
    - Add a mempool admission policy: size cap (config), fee-based
      eviction, per-address rate cap.

1.3 Block Validation Engine
    - server/blockchain/validation/block.ts
        * verifyBlock(block, prevBlock, utxoView): ValidationResult
        * Checks: parent linkage, timestamp window (±2h), merkle root,
          header hash < target, coinbase reward <= subsidy + fees,
          all tx pass verifyTransaction, no duplicate txids.
    - Apply verifyBlock on EVERY code path that appends a block:
      mining, peer gossip receipt, DB rehydration at startup.
    - Startup: re-validate the last N (default 100) blocks and refuse
      to boot on violation (log + alert).

1.4 Real PoW Mining
    - server/blockchain/mining.ts
        * mineBlock(header, target): nonce-search loop with
          @noble/hashes double-SHA256.
        * Difficulty retarget every 2016 blocks (config) to maintain
          ~10s block time; clamp to [minDifficulty, maxDifficulty].
        * Persist cumulative chain-work alongside each block.
    - Remove any "simulated" mining loops.

PHASE 1 ACCEPTANCE:
  - `grep -ri "private_key\|mnemonic" server/ --include='*.ts'` only
    matches keyvault.ts and reveal endpoint.
  - A curl with a tampered signature is rejected with error code

  - A double-spend attempt within the same block is rejected with
    TX_DOUBLE_SPEND.
  - A block with a wrong merkle root is rejected with BLOCK_BAD_MERKLE.
  - Unit tests for validation module pass at >= 90% coverage.

PHASE 3 — P2P NETWORK & CONSENSUS
──────────────────────────────────────────────────────────────────────
3.1 libp2p node
    - server/p2p/node.ts
        * Create libp2p node with TCP, noise encryption, mplex muxer.
        * Peer discovery: mDNS (local dev) + configurable bootstrap list
          (env: BOOTSTRAP_PEERS=csv).
        * Identity persisted to disk (server/data/p2p-identity.key) and
          encrypted with the master key.
    - server/p2p/protocols/
        * gossip-blocks.ts: broadcast new blocks; receive → verifyBlock
          → append or trigger reorg.
        * gossip-tx.ts: broadcast mempool txs; receive → verifyTransaction
          → admit to mempool.
        * sync-headers.ts: peer handshake exchanging tip height + hash;
          if peer ahead, request block range (batched, max 500/request).
        * sync-blocks.ts: range-fetch with validation per block.

3.2 Fork choice & reorg
    - server/blockchain/chain.ts
        * Track cumulative chain-work, not just height.
        * On peer block with higher work: attempt reorg — walk back to
          common ancestor, validate new path, swap chain tip atomically
          inside a DB transaction.
        * Refuse reorg if depth > MAX_REORG_DEPTH (default 12); emit
          CRITICAL alert + halt gossip acceptance until operator
          intervention.
    - Add AuditLog entries for every reorg (depth, from, to, reason).

3.3 Sync strategy
    - On startup: connect to bootstrap peers, run sync-headers; if
      behind, sync-blocks, then resume gossip.
    - Periodic anti-entropy: every 60s exchange tips with all peers;
      if any peer has higher work, sync.
    - Reject blocks with timestamps > 2h in the future or > 2h older
      than the median of the last 11 blocks.

3.4 Difficulty retarget
    - Every 2016 blocks: new_target = old_target * (actual_time / expected_time)
      clamped to [target * 0.25, target * 4].
    - Enforce retarget rule in verifyBlock: peers cannot submit a
      block with a target that violates the retarget math.

PHASE 3 ACCEPTANCE:
  - Two CreedChain nodes started locally discover each other via mDNS
    and stay in sync (both tips advance together after mining on
    either node).
  - Mining on node A appears on node B within 2 seconds.
  - A fork induced by disconnecting and mining on both sides is
    resolved by longest-work rule when reconnected; AuditLog shows
    reorg entry.
  - A peer sending a malformed block is disconnected after N violations.
